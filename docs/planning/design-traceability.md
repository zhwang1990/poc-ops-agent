# 设计范围追溯清单

本文件用于约束项目规划必须严格遵循《企业级智能运维 Agent 开放底座架构设计蓝图 V8.1》。

P1 只读诊断 MVP 已于 2026-07-01 完成验收。当前阶段进入 P2 受控变更试点，所有新增能力仍必须遵守单组织、自研自用和不开放生产写执行的产品边界。

## 产品边界

- 系统为公司内部自研自用。
- 系统为单组织部署。
- 设计中没有租户或多租户概念。
- 不规划租户标识、租户隔离、租户路由、租户计费和租户管理。
- 用户权限边界使用设计中的用户、角色、Skill Category、参数权限、目标环境和审批机制表达。

## 为实现设计目标而补充的工程机制

以下内容不是新增产品能力，而是为了让设计中的安全、恢复、审计和生产运行目标能够落地：

- 持久化工作流作为执行事实源。
- 幂等键、补偿和人工接管。
- Skill 签名、灰度和回滚。
- AgentScope 文件系统 Skill 与平台契约分离：`backend/skills/<skill>/SKILL.md` 面向 Agent，`backend/contracts/skills/packages/<skill>/` 面向注册、签名、Schema 和测试。
- 动态模型供应方设置用于替代静态环境变量配置：只支持单组织内部管理员维护 OpenAI-compatible 供应方，API Key 加密保存并只返回指纹，测试配置只返回脱敏连通性状态，不新增租户、计费、外部客户接入或模型市场能力。
- 强类型 CommandEnvelope 和版本化跨模块契约。
- 受限 Worker、短期凭据和受控网络出口。
- 测试评测、安全验证、故障注入和发布门禁。
- 在没有外部 IdP 的部署中，由 M01 实现正式内建身份域、账号会话和受控密码重置，但不得改变单组织产品边界。
- M09 操作台首轮重写采用 JavaScript / JSX、JSDoc、TypeScript `checkJs`、Zod、Vitest 和 Playwright，属于前端工程落地机制，不新增产品边界。
- SQL 工作台在 P1 已提供连接目录、SQL 校验、开发/测试环境受控单条 `SELECT` 执行和 DML 静态预检报告；任何开发环境写执行仍按 P2 受控变更试点追溯到策略、工作流、Worker 和审计链。
- 发布中心在 P2 作为非生产受控变更工程机制落地：配置、凭据、制品或脚本 Profile、确认、执行、回滚和日志分析都必须受版本化契约、服务端策略、持久化工作流、Worker 隔离、审计和可观测性约束；该机制不新增生产发布能力、任意脚本执行、多租户或外部客户接入。

这些机制不得改变产品边界。需要新增产品能力时，必须先获得用户确认并更新设计。

## 后续评估能力

### 长期记忆

当前不交付通用长期记忆能力，也不把长期记忆纳入 P2 受控变更试点的启动范围。后续如建设，必须作为独立设计议题评审，并拆分为可授权、可审计、可引用、可删除、可评测的平台能力，而不是模型黑盒记忆。

长期记忆的候选范围仅限以下受控类型：

- 知识记忆：运维手册、故障案例、发布记录、会议纪要等可引用知识，通过 RAG 或等价检索能力提供回答，回答必须带来源引用或明确无命中。
- 任务记忆：历史 workflow、Tool 结果、处置记录和中间制品，由 M05 工作流和 M06 制品黑板承载事实源。
- 偏好记忆：用户常用环境、筛选条件和界面展示偏好，只能影响操作台体验，不得影响授权、审批或执行边界。
- 经验记忆：故障模式、处置模板和规则建议，必须经过评审、版本化、测试和回滚管理，不得由模型自动沉淀后直接用于执行。

长期记忆不得替代 M01 身份、M02 授权、M05 工作流事实源、M07 Worker 隔离、M09 强类型事件或 M10 审计观测。Redis、ChatMemory、AgentScope memory、session state、chat history 和浏览器缓存都不得作为长期记忆事实源或执行事实源。

## 禁止擅自引入的能力

- 多租户和商业化计费。
- 面向外部客户的开放平台能力。
- 未经审批的生产写操作。
- 绕过环境策略、分析快照、持久化工作流或审计链的开发测试写操作。
- 任意脚本生成后直接执行。
- 由人格或 Prompt 降低组织安全要求。
- 未经独立设计评审的通用长期聊天记忆、模型黑盒记忆或跨任务自动经验沉淀。
- 与设计目标无关的技术平台化扩展。
- 把 `local-oidc` / Mock OIDC 直接当成生产身份方案。

## 规划变更检查

每次新增模块、任务、契约或基础设施前，回答：

1. 它对应 design 的哪一章节或目标？
2. 它是产品能力，还是实现该产品能力的工程机制？
3. 它是否改变自研自用、单组织部署的产品边界？
4. 它是否引入 design 未定义的新角色、新权限或新业务流程？
5. 如果改变产品边界，是否已经获得用户确认？
