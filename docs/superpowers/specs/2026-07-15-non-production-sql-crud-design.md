# SQL 工作台非生产受控 CRUD 设计

## 1. 背景与目标

SQL 工作台已完成单条 `SELECT` 的受控执行和 DML 静态预检，但控制面在 DML 提交前固定拒绝请求。P2 将在既有 M02、M05、M07 和 M09 边界内开放非生产受控 CRUD，使操作人能够在工作台中执行单条 `INSERT`、`UPDATE` 和 `DELETE`。

本设计的目标是：

- 仅在 `dev`、`sit` 和 `uat` 执行受控单条 DML。
- 为每次写执行提供可验证的策略、确认、幂等、持久化工作流、审计和恢复状态。
- 使用受限 Worker 的短事务执行，并保持控制面不直接使用目标系统凭据。
- 保持既有只读查询链路和生产环境只读边界不变。

## 2. 范围与非目标

### 2.1 范围

- 单条 `INSERT`、`UPDATE` 和 `DELETE` 的预检、提交、执行结果和状态展示。
- 控制面策略校验、DML 确认、执行绑定、持久化工作流、统一审计和人工接管状态。
- Worker 二次校验、按环境写执行功能开关、最小权限写凭据和短事务提交或回滚。
- 覆盖 H2 的端到端验证，并保留适配其他已登记非生产 SQL 连接的边界。

### 2.2 非目标

- 不开放生产环境 DML、DML 预检或 DML 提交。
- 不支持多语句、DDL、事务脚本、跨标签事务、交互式提交或回滚句柄。
- 不允许模型自动授权、自动确认或自动执行 DML。
- 不新增部署服务、独立模块编号或私有审计表。

## 3. 模块职责

| 模块 | 职责 |
|---|---|
| M09 SQL 工作台 | 维持编辑、预检、确认和结果展示；将通过校验的 DML 提交给工作流入口，不直接执行。 |
| M02 策略与审计 | 延续服务端策略决策，并通过统一 `AuditTrail` 记录受控 DML 的关键阶段。 |
| M05 工作流 | 创建、去重、持久化和恢复 DML 工作流；在提交 Worker 前持久化授权绑定和执行状态。 |
| M07 Worker | 校验签名、过期时间、环境、连接出口、写能力和单条 DML 限制；在短事务中执行。 |

## 4. 契约与数据模型

现有 `SqlDmlCommitRequest` 与其中的 `SqlQueryRequest.idempotencyKey` 继续作为操作台提交边界。实现必须为 DML 工作流新增版本化强类型契约，用于表达：

- DML 工作流标识、执行请求标识、操作者、目标环境、连接和 Schema。
- SQL 哈希、规范化参数哈希、预检哈希、策略决策标识和策略版本。
- 确认内容的哈希、风险集合和确认时间。
- 工作流状态、尝试编号、Worker 过期时间、影响行数、失败码和人工接管原因。

执行绑定由连接、环境、Schema、动作、SQL 哈希、参数哈希、预检哈希、策略版本和确认内容构成。相同幂等键仅在操作者、环境和执行绑定完全一致时复用已有工作流；同键不同绑定必须拒绝，不能重新执行。

任何跨模块请求均使用版本化契约和强类型信封，不能以无约束映射传递 DML 元数据。Worker 请求必须可验证地关联到已持久化的工作流和执行绑定。

既有只读 `SqlQueryExecutionRequest` v1 保持不变。DML 提交和 DML 影响预览分别使用独立的 v1 执行信封，避免为写路径破坏现有只读消费者。影响预览的可返回列和需掩码列由服务端 DML 规则显式声明；未声明预览列时只返回影响计数和不可验证项，不返回样本数据。

## 5. 提交流程

1. 操作台对单条 DML 调用预检接口，显示语句类型、风险、拒绝原因和不可验证项。
2. 操作人提交 `COMMIT_DML`。控制面重新校验连接能力、目标环境、语句类型和预检结果，拒绝生产、多语句、DDL 及未授权目标。
3. 对存在风险的语句校验确认内容与当前 SQL 哈希和风险集合一致；无 `WHERE` 的 `UPDATE` 和 `DELETE` 必须完成二次确认。
4. 控制面建立执行绑定，并通过 M05 先持久化工作流、幂等关系、初始语义事件和审计事件。
5. M05 创建具备明确过期时间的 Worker 执行请求。控制面只经受签名保护的受限 Worker 客户端提交该请求。
6. Worker 再次校验环境开关、连接出口、凭据权限、请求过期时间和 DML 子集，在一次短事务中执行。成功自动提交，明确失败自动回滚。
7. M05 持久化完成、失败或结果未知状态，并写入统一审计链。操作台使用服务端状态和结果渲染影响行数或失败码。

## 6. 状态、恢复与回滚

工作流至少需要区分已创建、已确认、已提交 Worker、已成功、已明确失败和结果未知/人工接管状态。

- Worker 返回明确失败时，工作流记录终态失败；短事务由 Worker 回滚。
- Worker 返回成功时，工作流记录影响行数、结果引用和完成审计事件。
- 网络中断、超时或 Worker 未返回终态时，工作流进入结果未知状态，禁止自动重放 DML。系统保留请求、绑定和审计证据，交由人工确认目标系统状态后接管。
- 同一执行绑定的重复提交必须返回已保存的状态或结果，不能生成第二次写执行。
- 功能开关按 `dev`、`sit`、`uat` 独立配置且默认关闭。回滚时关闭该环境开关、撤销 Worker 写凭据、拒绝未开始的授权；只读查询继续可用。生产环境没有 DML 开关。

## 7. 安全与审计

- 服务端策略为唯一授权点；浏览器只渲染服务端决策，不能自行放宽 DML 条件。
- 审计使用统一 `AuditTrail`，记录创建、确认、提交、完成、失败、结果未知和人工接管。
- 审计、日志和事件只记录连接、环境、表、哈希、风险、工作流标识、操作者和影响行数；不得记录原始参数、长期凭据或敏感结果。
- Worker 使用最小权限写身份、受控出口和短期凭据；控制面不使用目标数据库长期凭据。
- Worker 和控制面均执行环境及 DML 子集校验。生产请求在契约、控制面和 Worker 边界均保持不可执行。

## 8. 界面行为

工作台继续采用现有预检和确认交互。只有服务端连接能力、非生产环境和环境功能开关均满足时，提交入口才可用。结果区展示工作流标识、当前状态、影响行数以及可审计的失败码；不得从展示文本推断授权或执行状态。

## 9. 验收与测试

- 契约测试：DML 工作流和 Worker 执行信封的版本化、必填字段、绑定和兼容性。
- 控制面测试：环境、连接、Schema、单语句、风险确认、功能开关、策略拒绝和幂等冲突。
- M05 测试：工作流先持久化后提交 Worker、重复提交复用、明确失败持久化、结果未知人工接管和审计顺序。
- Worker 测试：签名、过期时间、非生产环境、出口、写权限、单条 DML 和短事务提交/回滚。
- 端到端测试：在 H2 非生产连接完成 `INSERT`、`UPDATE`、`DELETE`，并通过 `SELECT` 验证数据和影响行数；验证生产环境和功能开关关闭时均拒绝写执行。
- 前端测试：提交入口状态、确认载荷、服务端返回的工作流状态、影响行数和失败状态渲染。

## 10. 交付证据

完成实施前必须更新 M09 P2 计划状态、设计追溯、P2 运行手册、功能开关和回滚说明，并完成 M02、M05、M07 的安全评审与端到端验收。生产环境 SQL 工作台始终只允许查询。
