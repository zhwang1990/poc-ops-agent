# M09 第三方组件声明页面设计

- 日期：2026-07-04
- 相关模块：M09、M00、M11
- 目标阶段：P2 受控变更试点
- 状态：待实施设计

## 1. 背景与目标

操作台已经引入 React、React Router、Zod、Lucide React、CodeMirror 等第三方组件，后续如果复制、改造或打包 queFork 代码、样式、资源或其他开源组件，也需要在分发软件时保留对应版权声明和许可证声明。

本设计新增一个登录后可访问的第三方组件声明页面，用于集中展示运行时随操作台分发的第三方开源组件信息。页面只承担合规披露和查阅职责，不提供授权、不改变审批、不作为安全状态或执行事实源。

目标：

1. 为第三方许可证声明提供稳定、可被用户查阅的入口。
2. 将声明页面放在 M09 操作台信息架构中，不挤占高频业务导航。
3. 以静态、可审查的数据结构维护首版清单，后续可由 M11 或工具链自动生成。
4. 明确 queFork 等组件只有在确认实际复制、修改或打包分发后才进入声明清单。

## 2. 范围与非目标

首版范围：

- 新增受保护路由 `/third-party-licenses`。
- 新增 M09 前端页面“第三方组件声明”。
- 在帮助页增加“法律与开源声明”相关入口。
- 在操作台侧边栏底部增加低权重“法律信息”入口。
- 维护一份前端静态声明数据，覆盖运行时随操作台分发的组件。
- 页面展示组件名、版本或 commit、来源、许可证、版权声明、使用范围和许可证文本。

明确不包含：

- 不新增后端 API。
- 不新增跨模块契约。
- 不新增授权、审批、审计或工作流能力。
- 不把页面放入主业务导航。
- 不自动扫描 `node_modules` 或 Maven 依赖树。
- 不声明未实际分发的组件。
- 不提供法律意见或替代正式法务审查。

## 3. 页面位置方案

### 3.1 方案 A：独立页加低权重入口

新增 `/third-party-licenses` 独立页面，受 `ProtectedRoute` 保护。入口放在帮助页和侧边栏底部法律信息区。

优点：

- 声明内容独立、清晰，后续清单变长也不会污染帮助页正文。
- 不占用主导航的高频业务位置。
- 可在后续接入自动生成清单时保持页面路由不变。

缺点：

- 需要新增一个页面、路由和少量导航入口。

### 3.2 方案 B：仅作为帮助页章节

在 `/help` 中增加“开源声明”章节。

优点：

- 改动最小。

缺点：

- 法律披露内容和产品手册混在一起。
- 组件清单增长后会影响帮助页的查阅效率。

### 3.3 方案 C：主导航独立入口

在主侧栏增加“开源声明”导航项。

优点：

- 可见性最高。

缺点：

- 声明页不是日常运维工作流，会增加主导航噪声。
- 当前主导航已经承载 Agent、SQL、发布、审计等高频业务入口。

采用方案 A。

## 4. 信息架构

路由：

- `/third-party-licenses`

入口：

- 帮助页：增加“法律与开源声明”帮助章节或入口卡片，链接到 `/third-party-licenses`。
- 侧边栏底部：在主导航列表之外增加低权重文本链接“法律信息”，指向 `/third-party-licenses`。

入口规则：

- 主导航不新增“第三方组件声明”业务项。
- 侧边栏折叠为图标模式时，该入口需要保留可访问名称和 `title`。
- 帮助页搜索应能通过“开源”“许可证”“MIT”“第三方组件”“queFork”等关键词命中该入口。

## 5. 页面内容结构

页面标题：第三方组件声明

页面说明：

- 说明本页列出随操作台分发的第三方开源组件。
- 说明声明内容仅用于版权和许可证披露。
- 说明平台自身授权、审批、审计、Worker 隔离和安全边界仍以服务端策略和工作流事实源为准。

主体分区：

1. 摘要区
   - 已声明组件数量。
   - 覆盖范围：操作台运行时组件。
   - 更新来源：仓库静态声明数据。
2. 组件列表
   - 组件名称。
   - 版本、包版本或 source commit。
   - 来源链接。
   - 许可证。
   - 使用范围。
   - 版权声明摘要。
3. 许可证正文
   - 展示选中组件的许可证全文。
   - 对 MIT、ISC、Apache-2.0、BSD 等文本保留原始英文，不翻译协议标准文本。
4. 维护说明
   - 新增运行时第三方组件时，需要同步更新声明数据。
   - 复制或修改第三方源码、样式、资源时，需要保留原始版权和许可证声明。

## 6. 数据设计

首版使用前端静态数据文件维护声明清单，例如：

```text
frontend/operator-console/src/features/third-party-licenses/third-party-licenses-data.js
```

每个组件条目需要包含：

- `id`：稳定英文标识。
- `name`：组件名称。
- `version`：包版本、源码版本或 commit。
- `homepageUrl`：项目主页或仓库地址。
- `licenseId`： SPDX 风格许可证标识，例如 `MIT`。
- `copyright`
- `usage`
- `noticeText`：版权声明和许可证正文。

数据规则：

- `version` 不允许为空；没有 semver 的源码组件必须记录 commit 或来源快照标识。
- `noticeText` 必须包含原始版权声明和许可证许可声明。
- queFork 只有在确认平台实际复制、修改或打包其代码、样式、资源或重要片段后才进入清单。
- 如果实施时仍无法在仓库或制品中确认 queFork 集成事实，不得硬编码 queFork 声明；应先用已确认随操作台分发的运行时依赖填充页面。
- 开发、测试和构建工具可以在后续 `THIRD_PARTY_NOTICES` 或发布制品声明中补充；页面首版优先覆盖浏览器运行时分发内容。

## 7. 交互与视觉原则

页面属于合规信息查阅，不是营销页或操作工作台。视觉风格应克制、可扫描、可复制。

布局：

- 沿用 `WorkspacePageFrame` 和 `WorkspaceStatusBar`。
- 左侧或上方提供组件列表。
- 主区域展示许可证详情。
- 不使用弹窗作为首要展示方式。
- 不使用装饰性大图、渐变英雄区或与业务无关的卡片堆叠。

可访问性：

- 组件列表使用按钮或链接时必须有明确可访问名称。
- 当前选中组件需要有可感知状态。
- 许可证正文使用可滚动文本区域或普通正文区域，避免内容溢出页面。
- 页面在主侧栏折叠状态下仍可访问。

复制能力：

- 可以提供“复制许可证文本”按钮，但该按钮只复制当前选中组件的声明文本。
- 复制失败时显示普通状态反馈，不写入审计或工作流。

## 8. 安全、合规与模块边界

安全边界：

- 页面不得包含授权逻辑。
- 页面不得从展示文本推断任何安全状态。
- 页面不得展示密钥、内部凭据、生产数据或目标系统配置。
- 页面不得调用目标系统、Worker 或模型接口。

模块边界：

- M09 负责页面展示和前端静态数据。
- M00 可在后续补充仓库级合规规范或贡献者说明。
- M11 可在后续补充依赖许可证检查、生成清单和发布门禁。

合规边界：

- 本页面用于履行第三方开源组件声明义务。
- 本页面不替代正式法务审查。
- 对协议标准文本保留英文原文；页面说明和维护说明使用中文。

## 9. 测试与验收

组件测试：

- 路由 `/third-party-licenses` 在登录后渲染页面标题。
- 页面展示至少一个已确认运行时组件。
- 组件列表切换后展示对应许可证正文。
- 帮助页搜索“开源”“许可证”“MIT”能找到声明入口。
- 侧边栏底部入口指向 `/third-party-licenses`。

静态检查：

- `npm run check`
- `npm run lint`
- `npm run test`

浏览器验收：

- 桌面视口下页面无文字重叠。
- 侧边栏展开和折叠状态都能进入声明页。
- 许可证正文长文本可读、可滚动，不遮挡页面其他内容。

完成标准：

- 运行时分发组件清单准确，不包含未确认使用的组件。
- 每个组件条目包含版权声明和许可证文本。
- 页面没有新增后端能力或绕过现有安全链路。
- 相关帮助内容和页面测试同步更新。

## 10. 后续演进

后续可以独立规划以下能力：

- 从 `package-lock.json` 和 Maven 依赖树生成候选许可证清单。
- 在 CI 中检查新增运行时依赖是否补充声明。
- 在发布制品中生成 `THIRD_PARTY_NOTICES` 文件。
- 将页面数据从静态文件切换为构建时生成产物。

这些能力属于工具链和发布门禁增强，不属于首版页面范围。
