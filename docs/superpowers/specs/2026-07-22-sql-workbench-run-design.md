# SQL 工作台统一运行入口设计

## 目标

将 SQL 工作台从“只读执行”和“提交当前受控 DML”两个操作入口，调整为符合 IDE 习惯的单一“运行”入口。操作者只需关注正在执行的 SQL 和必要的风险提示，不需要理解受控 DML、预检请求、Worker 或确认码等内部实现术语。

本设计只改变非生产 SQL 工作台的交互和展示文案，不放宽服务端授权、安全策略、审计、幂等、预检或执行隔离。

## 用户交互

1. 编辑器工具栏只保留一个主操作“运行”。
2. 输入 `SELECT` 等只读 SQL 时，“运行”沿用现有只读执行链路。
3. 输入 `INSERT`、`UPDATE` 或 `DELETE` 时，非生产连接的“运行”自动进入现有预检和提交链路，不再要求先切换事务模式，也不显示“提交当前受控 DML”。
4. 服务端预检未报告风险时，客户端直接提交执行请求；这是用户的一次“运行”操作。
5. 服务端预检报告风险时，显示“确认执行”对话框。对话框仅展示预计影响、风险原因和样本数据；确认按钮为“执行”，取消按钮为“取消”。
6. 生产连接上的写 SQL 不执行。界面以“生产环境不允许执行写操作”说明原因，不显示内部能力或协议名称。
7. 成功结果统一显示“执行完成，影响 N 行”；失败结果说明可操作原因，不暴露 Worker、确认码或内部动作名称。

## 安全与数据流

前端根据当前 SQL 类型和连接环境选择既有服务端接口：只读 SQL 使用 `RUN_READ_ONLY`，非生产写 SQL 先使用 `PREFLIGHT_DML`，再使用 `COMMIT_DML`。接口、契约版本、幂等键、预检回执、服务端策略、持久化工作流、审计事件和受限 Worker 保持不变。

无风险写操作仍会携带既有确认数据，满足服务端契约；该数据不作为用户界面概念展示。风险写操作必须在用户确认后才提交。生产写操作继续由服务端能力和策略双重拒绝。

## 组件调整

- 用“运行”替换现有编辑器执行按钮和事务控制组中的写操作提交按钮。
- 删除面向操作者的“事务模式”“受控 DML”“DML 提交”等文案与入口。
- 保留风险确认对话框、影响预览、未知结果人工接管和结果面板，但将可见文案改为执行语义。
- 保留连接管理中的内部能力配置；该能力不在常规操作页面展示。

## 错误处理

- 不支持的写 SQL：说明当前连接或环境不允许写操作。
- 预检拒绝：说明 SQL 未通过安全校验，并展示服务端返回的可操作拒绝原因。
- 预检缺少影响预览、提交失败或未知结果：沿用现有恢复与人工接管语义，改用面向操作者的文案。
- SQL 变更期间仍按既有规则轮换幂等键，禁止重复提交旧请求。

## 验收与测试

1. 非生产 `INSERT`、带 `WHERE` 的 `UPDATE` 和带 `WHERE` 的 `DELETE` 都可以通过唯一“运行”入口完成执行。
2. 无 `WHERE` 的 `UPDATE` 或 `DELETE` 先显示“确认执行”，取消后不提交，确认后才提交。
3. `SELECT` 继续通过“运行”返回查询结果。
4. 生产写 SQL 被拒绝，且不暴露内部能力名称。
5. 现有预检、确认、幂等重试、未知结果人工接管与审计相关测试继续通过，并补充上述交互测试。
